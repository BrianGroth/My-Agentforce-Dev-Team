My Dev Team — Agent Descriptions

A 6-agent personal team for Claude Code covering the full Salesforce/Agentforce DevOps Lifecycle (ADLC), from design through production monitoring. Say "My Dev Team" to Claude Code and it routes your request through the right agent, or sequence of agents, instead of working ad hoc, with The Orchestrator Agent taking the lead to work with you and coordinate the other 5 agents.

Each agent has a "The … Agent" display name (The Architect Agent, The Builder Agent, and so on) and announces itself when it works, so you always see which teammate is active. Each one plans, executes, and self-corrects — it states what it's about to do, does it, and checks its own output against the phase gate before handing off. And because Claude Code can run multiple agents at the same time, the team fans out genuinely independent work in parallel to move faster, while keeping the phase gates intact.

Use the descriptions below as a reference for understanding what each agent does, what it receives and produces, and how the team fits together.

Reading the arrows

Feedback / route-back (red solid) — expected, routine. Work wasn't ready; it goes back to be fixed and re-submitted. QA finds a bug → sends it to Builder. QA finds a design gap → sends it to Architect. Shipper discovers untested surface → pulls QA back in. These are normal loop mechanics; the receiving agent fixes the specific issue and the phase proceeds on the next pass.

Escalation (blue dashed) — the normal route has already failed, or the situation is too severe for a fix-forward approach. Two cases: (1) Circuit breaker — the same case has already bounced once through the feedback path and failed again; on the second bounce Builder stops trying and escalates up to Architect instead, because a design-level review is needed, not another patch attempt. (2) Rollback — Sentinel finds a severe live regression and calls Shipper for an immediate undo rather than "fix it and redeploy." It is a priority interrupt, not a retry.

The short version: feedback means "not done yet, go fix it"; escalation means "the fix-it path has failed or isn't appropriate — take a fundamentally different action."

The Orchestrator Agent

Routing name: orchestrator  ·  Model: Opus (the only team member not on Sonnet)  ·  Tools: Task, Read, Write, Edit, Glob, Grep, Bash  ·  Skills: none

The orchestrator is the single entry point for My Dev Team. It does not design, build, test, deploy, or monitor — it drives the five phase agents through a controlled loop until the stated goal is met, keeping the whole team on one project against one target org. It runs on Opus because it holds multi-phase context, runs the circuit breaker, and makes routing decisions across the full lifecycle; every bounded phase agent runs on Sonnet. Invoke it any time the user says "My Dev Team"; invoke a phase agent directly for single-phase, scoped work where the coordination overhead adds no value.

Its primary output is SOLUTION-BLUEPRINT.md: a living map of every component built, org-config steps not captured in metadata, and a rebuild-in-a-new-org checklist. It also owns the live ASCII status panel printed at every phase transition, and bootstraps the shared INCIDENTS.md and DECISIONS.md logs at project kickoff.

The sections below are what you will find inside orchestrator.md, grouped by purpose. Phase agents share a shorter common skeleton; this file is longer because it owns the coordination logic that no phase agent should hold.

The Architect Agent

  1. Name — Routing name: architect; display name: "The Architect Agent."
  2. Role — Owns Ideation & Design: discovers what is live in the target org, then produces the PRD and Agentforce agent spec that the rest of the team builds from.
  3. The problem it solves — Without an architect, builders design as they code, producing metadata that doesn't reflect the org's real state and specs that contradict each other mid-build.
  4. What it receives — An intake brief from the orchestrator naming the target org, the solution goal, the channel, and the RAG status.
  5. What it produces — A PRD-<solution>.md at the project root: the durable contract containing the agent spec, backing-asset inventory, sharing/security model, and RAG requirements.
  6. Exit gate — The PRD file exists at the project root, names the target org, lists every backing asset the builder will need, and the user has explicitly approved the design at the Design Review Gate.
  7. Salesforce skills it uses — Preloaded: salesforce-design (design workflow), salesforce-document (solution documentation, phase 10); dispatched on demand: platform-environment-validate, platform-architecture-analyze, platform-metadata-retrieve, platform-sharing-owd-configure, platform-sharing-rules-generate, agentforce-generate (agent spec authoring).
  8. Claude Code tools it needs — Read, Write, Edit, Glob, Grep, Bash, Skill, Task, WebFetch, WebSearch.
  9. Model — Sonnet; the design phase is bounded and skill-driven, so the cheaper model is sufficient.
  10. How it hands off forward — Delivers the completed PRD to the orchestrator, which then dispatches builder with a brief pointing at the PRD file.
  11. How it escalates backward — If qa or builder returns a design gap (not a code bug), the orchestrator routes it back to architect with the specific section to revise; architect updates the PRD and re-presents to the user.
  12. What it documents — Co-authors SOLUTION-DOC.md at phase 10 (owns sections A, B, C, D, E, F, G, I, and K.1/K.3/K.4/K.5; section H belongs to QA); logs non-obvious design decisions to DECISIONS.md; checks INCIDENTS.md before designing in any area with known history.
  13. When NOT to use it — Do not invoke architect to write Apex, LWC, or Flows (use builder), to run tests (use qa), or to package a release (use shipper).

The Builder Agent

  1. Name — Routing name: builder; display name: "The Builder Agent."
  2. Role — Owns Development: takes a finished, user-approved PRD and turns it into deployable Salesforce metadata — Apex, LWC, Flows, custom objects/fields, and the Agentforce agent bundle.
  3. The problem it solves — Without a dedicated builder, architects hand-wave implementation details and testers receive code written by whoever happened to be active, with no consistent quality bar.
  4. What it receives — A brief from the orchestrator pointing at the approved PRD, naming the target org and the DX project directory to commit into.
  5. What it produces — Authored metadata in the DX project (.agent bundle, Flows, Prompt Templates, Apex classes, Permission Sets, MIAW/ESD config) plus LSP-validated, commit-ready source on the feature branch.
  6. Exit gate — All metadata compiles/validates locally (LSP diagnostics pass), the DX project structure is intact, and the feature branch is pushed — qa can pull and run against it without manual setup.
  7. Salesforce skills it uses — Preloaded: salesforce-develop; dispatched: dx-project-create, agentforce-generate, platform-apex-generate, experience-lwc-generate, platform-custom-object-generate, platform-custom-field-generate, platform-validation-rule-generate, automation-flow-generate, platform-permission-set-generate, platform-lsp-integrate (LSP diagnostics).
  8. Claude Code tools it needs — Read, Write, Edit, Glob, Grep, Bash, Skill, Task.
  9. Model — Sonnet; code generation and metadata authoring are well-scoped tasks the smaller model handles reliably.
  10. How it hands off forward — Dispatches qa directly (via Task) with a brief pointing at the feature branch and the PRD's eval-set requirements; does not route through the orchestrator.
  11. How it escalates backward — If a qa failure traces to a design gap rather than a code bug, builder flags it to the orchestrator rather than patching around it; on a second qa bounce of the same case, the circuit breaker triggers and architect is brought in.
  12. What it documents — Checks INCIDENTS.md before touching any area with known bug history; does not write to DECISIONS.md directly, but may flag a decision to architect for logging.
  13. When NOT to use it — Do not invoke builder before a user-approved PRD exists (use architect first), and do not ask builder to write or run test classes (use qa).

The QA Agent

  1. Name — Routing name: qa; display name: "The QA Agent."
  2. Role — Owns Testing & Validation: runs the actual test suite and Agentforce eval set against the build, grades it against the OWASP LLM Top 10, and signs off explicitly before anything ships.
  3. The problem it solves — Without a QA agent, test coverage is self-assessed by the builder, eval sets are never run, and security grading is skipped under time pressure.
  4. What it receives — A brief from the orchestrator pointing at the feature branch, the PRD's eval-set requirements, and the target org to test against.
  5. What it produces — An explicit sign-off statement naming what was tested, the coverage percentage, the OWASP grade, and any known gaps — the artifact shipper requires before promoting.
  6. Exit gate — Apex coverage ≥ 75% org-wide with meaningful assertions, all eval-set cases pass, Code Analyzer findings addressed, OWASP LLM Top 10 grade recorded, and qa's sign-off committed to the branch.
  7. Salesforce skills it uses — Preloaded: salesforce-test, salesforce-document; dispatched: platform-apex-test-run, platform-apex-test-generate, dx-code-analyzer-run, platform-data-manage, agentforce-test (includes OWASP Mode C security grading).
  8. Claude Code tools it needs — Read, Write, Edit, Glob, Grep, Bash, Skill, Task.
  9. Model — Sonnet; test execution and result interpretation are bounded tasks, and the skills carry the domain-specific evaluation logic.
  10. How it hands off forward — Delivers the sign-off statement to the orchestrator; orchestrator dispatches shipper with that sign-off as a prerequisite artifact.
  11. How it escalates backward — Routes code bugs back to builder on the first failure; routes design gaps to architect; if builder's fix fails qa a second time, triggers the circuit breaker rather than sending it back a third time.
  12. What it documents — Co-authors SOLUTION-DOC.md at phase 10 (owns sections H, J, and K.2); logs escalated or stuck failures to INCIDENTS.md; logs non-obvious coverage or scope decisions to DECISIONS.md.
  13. When NOT to use it — Do not invoke qa to fix code (use builder), to design the agent spec (use architect), or to promote a release (use shipper).

The Shipper Agent

  1. Name — Routing name: shipper; display name: "The Shipper Agent."
  2. Role — Owns Deployment & Release: packages the build, promotes it through sandbox to production in dependency order, and manages Agentforce bundle versioning, activation windows, and rollback.
  3. The problem it solves — Without a dedicated shipper, deployments happen ad hoc, dependency order is guessed, production changes skip validation, and rollback plans exist only in someone's head.
  4. What it receives — A brief from the orchestrator confirming qa has signed off, pointing at the feature branch and the target org for promotion.
  5. What it produces — A successful deploy confirmation (metadata live in the target org), an activated BotVersion, and a prepared rollback path — the artifacts sentinel monitors against.
  6. Exit gate — platform-deploy-validate passes, user gives explicit go-ahead, platform-quick-deploy succeeds, BotVersion Status = Active, and the rollback plan is documented in the blueprint.
  7. Salesforce skills it uses — Preloaded: salesforce-release; dispatched: platform-metadata-deploy, platform-deploy-validate, platform-quick-deploy, platform-destructive-deploy, dx-org-manage, platform-manifest-generate; Agentforce publish/activate via sf agent publish|activate CLI directly.
  8. Claude Code tools it needs — Read, Write, Edit, Glob, Grep, Bash, Skill, Task.
  9. Model — Sonnet; deployment steps are procedural and skill-driven with clear pass/fail outcomes.
  10. How it hands off forward — Dispatches sentinel directly (via Task) to begin post-release verification; does not route through the orchestrator.
  11. How it escalates backward — If asked to ship untested work, pulls qa in before proceeding; if sentinel requests a rollback, treats it as a priority interrupt ahead of the normal queue.
  12. What it documents — Logs every release and rollback to INCIDENTS.md; logs non-obvious release strategy decisions (e.g. component-by-component vs. all-at-once) to DECISIONS.md.
  13. When NOT to use it — Do not invoke shipper before qa has signed off, and never ask shipper to fix a bug found post-deploy (route that to builder or architect via sentinel).

The Sentinel Agent

  1. Name — Routing name: sentinel; display name: "The Sentinel Agent."
  2. Role — Owns Monitoring & Tuning: verifies the live deployment, investigates debug logs and governor limits, and routes anything it finds back into the build loop rather than patching production directly.
  3. The problem it solves — Without a sentinel, post-release issues are discovered by end users, debug logs are never reviewed, and production patches bypass the test pipeline.
  4. What it receives — A brief from the orchestrator after every production promotion, naming the live org, the deployed agent bundle, and the channel to verify.
  5. What it produces — A verification record confirming live sessions resolve correctly, governor limits are within bounds, and no regression exists — or an incident log entry and a routed fix request if something is wrong.
  6. Exit gate — Live agent sessions resolve without errors, no governor-limit violations in debug logs, and the verification record is committed to the branch; this is the gate that releases phase 10 (documentation).
  7. Salesforce skills it uses — Preloaded: salesforce-observe; dispatched: platform-apex-logs-debug, agentforce-observe (session trace and conversation log analysis); runs agentforce-test Mode C on a schedule for ongoing OWASP security posture checks.
  8. Claude Code tools it needs — Read, Write, Edit, Glob, Grep, Bash, WebFetch, Skill, Task.
  9. Model — Sonnet; log analysis and session-trace interpretation are bounded, evidence-based tasks.
  10. How it hands off forward — On a clean verification, commits the verification record to the branch, which is the gate that releases phase 10 (documentation); on a clean ongoing posture check, updates the incident log with "no findings."
  11. How it escalates backward — Routes code-level fixes to builder; routes design-gap findings to architect; on a severe live regression, calls shipper directly to request a priority rollback without waiting for the user to intervene.
  12. What it documents — Logs every production incident, governor-limit finding, and rollback to INCIDENTS.md; every new production incident triggers a new entry in the eval set so the same failure cannot silently recur.
  13. When NOT to use it — Do not invoke sentinel before a live deployment exists, and never ask sentinel to write a fix (it investigates and routes; builder writes the patch).
